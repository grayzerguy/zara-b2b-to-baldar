# ארגז הכלים — טכניקות פרומפטינג

קרא את הקובץ הזה כשצריך טכניקה מעבר לחמש הלבנים הבסיסיות. כל טכניקה כאן עולה משהו (אורך, זמן, לפעמים דיוק), אז השתמש בה רק כשהיא פותרת בעיה ממשית.

## 1. דוגמאות (Few-shot)

**מתי:** כשמבקשים סגנון, טון, או מבנה חוזר שקשה לתאר במילים.
**איך:** דוגמה אחת עד שלוש של קלט→פלט, בפורמט זהה למה שיגיע באמת.

```
דוגמה:
קלט: "המשלוח שלי מתעכב שבוע ואף אחד לא עונה"
פלט: "היי, אני מצטער על העיכוב. בדקתי — המשלוח יצא היום ויגיע עד יום ג'.
מספר מעקב: 12345. אם משהו לא מסתדר, תכתוב לי ישירות."
```

**המלכודת:** המודל מחקה גם את מה שלא התכוונת — אורך, מבנה, אפילו סימני פיסוק. אם כל הדוגמאות שלך באורך שתי שורות, כל התשובות יהיו בשתי שורות. ודא שהדוגמאות מייצגות את המגוון שאתה רוצה.

## 2. שרשור מחשבה (Chain of Thought)

**מתי:** משימות עם היגיון רב־שלבי — חישובים, ניתוח נתונים, החלטות עם כמה שיקולים.
**איך:** "לפני שאתה עונה, פרט את השלבים שלך" או "חשוב שלב־שלב, ואז תן את התשובה הסופית".
**מתי לא:** משימות יצירתיות או פשוטות. שם זה רק מאריך את התשובה בלי לשפר אותה.

וריאציה שימושית: `"תכנן ראשי פרקים, הצג לי אותם ועצור. אכתוב 'המשך' כשאאשר."` — חוסך שכתוב של טקסט ארוך שהלך לכיוון הלא נכון.

## 3. משתנים לשימוש חוזר

כשהפרומפט אמור לרוץ שוב ושוב על קלט משתנה (בקוד, ב־API, או ידנית):

```
נתח את חוות הדעת הבאה וסווג לחיובי/שלילי/ניטרלי.

חוות הדעת:
{review_text}

החזר מילה אחת בלבד.
```

הפרד את המשתנה משאר הטקסט בשורות ריקות או בתגית — `<review>...</review>`. זה מונע מהמודל להתבלבל בין ההוראות לבין הקלט, במיוחד כשהקלט ארוך או מכיל בעצמו טקסט שנראה כמו הוראה.

## 4. פלט מובנה (JSON / CSV)

תן סכימה עם שמות שדות אמיתיים וטיפוסים, לא תיאור מילולי:

```
החזר JSON תקין בלבד, בלי טקסט לפני או אחרי, במבנה:
{
  "name": "string — שם מלא כפי שמופיע במסמך",
  "amount": "number — סכום בשקלים, בלי סימן מטבע",
  "date": "string — פורמט YYYY-MM-DD",
  "confidence": "high | medium | low"
}
אם שדה חסר במסמך — החזר null, אל תנחש.
```

שתי השורות הקריטיות: **"בלי טקסט לפני או אחרי"** (אחרת תקבל "בטח! הנה ה־JSON:") ו**"אל תנחש"** (אחרת תקבל שדות ממולאים בהמצאות).

## 5. קריטריון עצירה / התמודדות עם חוסר ידיעה

הסיבה מספר אחת להזיות: הפרומפט לא אמר מה לעשות כשאין תשובה. תמיד תן מוצא:

- "אם המידע לא מופיע במסמך — כתוב 'לא נמצא במסמך'."
- "אם הבקשה לא ברורה — שאל שאלה אחת במקום לנחש."
- "בסס את התשובה רק על הטקסט שסופק, לא על ידע כללי."

## 6. תפקיד — כמה ספציפי?

| ניסוח | איכות |
|---|---|
| "אתה עוזר מועיל" | חסר ערך — זו ברירת המחדל ממילא |
| "אתה מומחה שיווק עולמי" | חלש — תארים לא משנים התנהגות |
| "אתה כותב תוכן שמתמחה בדפי נחיתה למוצרי B2B בישראל" | טוב — מגדיר תחום, קהל וסוג תוצר |

תפקיד עובד כשהוא **מצמצם את מרחב האפשרויות**. "מומחה" לא מצמצם; "כותב דפי נחיתה ל־B2B" מצמצם.

## 7. הפרדה בין System ל־User

- **System prompt** — מה שקבוע בכל שיחה: זהות, כללי טון, פורמט, איסורים.
- **User prompt** — המשימה הספציפית של הפעם.

הטעות הנפוצה: לדחוס משימה חד־פעמית לתוך ה־System. אחר כך הסוכן מנסה לבצע אותה בכל שיחה חדשה. מבחן פשוט: אם משפט לא נכון לכל שיחה עתידית — הוא לא שייך ל־System.

## 8. הבדלים בין מודלים

- **Claude** — מגיב טוב לתגיות XML (`<context>`, `<task>`) ולהסברי "למה". סובל פרומפטים ארוכים ומובנים.
- **GPT** — מגיב טוב לרשימות ממוספרות ולכותרות Markdown. עדיף לקצר.
- **Gemini** — מעדיף הוראות ישירות ופורמט פלט מפורש בסוף הפרומפט.

זה כיול עדין, לא הבדל מהותי. פרומפט טוב עובד בכולם; ההבדלים נכנסים לתמונה רק כשמשהו כבר עובד ורוצים לסחוט עוד אחוזים.
